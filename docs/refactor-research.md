# 重构调研：错误闭环、统一 UI 与本地 MCP

日期：2026-11-16。本文保留实施前调研快照；后续已实施第 1、2 项，当前契约与验收边界见 [ui-components.md](ui-components.md)。以下“当前”“建议”均指调研时点。

## 目标与已确认范围

1. 用户发起的操作发生失败、部分失败或清理失败，必须有可见结果和可追溯详情。
2. 参考相邻 `tyranor-next/AGENTS.md` 的公共组件规范，统一按钮、条目、输入、弹窗、底部抽屉和侧栏。
3. 后续新增本地 MCP 端口，让同机 Android Agent 调用 `uu`、运行 `uut`，编排解包、汉化处理和封包。

本轮只调研，不改变运行行为；不将当前 Views UI 迁移为 Compose，也不启动服务器。

## 代码现状与证据

### 错误链路

- `model/ExtractCounts.kt` 已有 `ExtractCounts`、`ExtractOutcome`，但缺少统一错误码、阶段和任务身份。
- `archive/ArchiveExtractor.kt:extractByFormat` 将异常转换为结果；调用者必须检查结果，否则不会自动中止。
- `extract/PreviewFlow.kt:mergeIntoArchive` 保存源/目标解包结果却不检查，随后继续封包。另有源先解、目标后解的覆盖顺序与注释意图不符。
- 同一合并流程只占 `merge` 伪槽；普通格式任务仍可能访问相同原生进度与 CANCEL。伪槽只能串行化合并之间的访问。
- `terminal/UuCommands.kt` 有退出码与集中异常捕获，但主要输出文本；不应让 MCP 反向解析本地化文本判断成败。
- `App.kt` 目前只初始化颜色 token；未发现统一任务日志服务。
- Rust 中部分目录创建和删除使用 `let _ = ...`；需逐处区分正常的“已不存在”和真正失败。删除失败不能覆盖最初的解码错误。

Kotlin 静态模式盘点：空 catch 13 处/6 文件；runCatching 77 处/21 文件；getOrDefault 35 处/15 文件；getOrNull 54 处/19 文件。这是审计候选，不是已确认缺陷数量。正常探测不匹配、空结果不等于失败。

### UI

- `ui/kit.kt` 已有文本、图标、卡片、等宽行等函数；尚未覆盖完整的语义按钮、设置条目和窗口壳。
- `res/values/dimens.xml` 已有间距、字号、栏高与圆角；`util/Constants.kt` 的 `C` 已承担颜色入口，应演进已有体系，避免新增平行 token 表。
- `ui/DialogHost.kt` 已集中 tab 归属、触摸护盾、停靠方式与关闭清理。它是窗口行为基础，重构时应保留其契约。
- `activity_main.xml` 的侧栏仍为独立的 260dp 宽布局；`bookmarks/Bookmarks.kt` 使用系统单行列表，再单独设置字号颜色。
- 静态盘点：AlertDialog.Builder 93 处/27 文件，原始 Toast 40 处/10 文件。它们表明公共入口覆盖不足，并不代表每一处外观都不同。

### 自动化

- 未在 app/crates/scripts 中发现 MCP 服务实现；Manifest 当前没有 INTERNET 权限和服务声明。
- `MainActivity.handleUutIntent` 已提供脚本启动入口，但执行仍通过界面进入。
- `terminal/Uut.kt` 主要负责解析和语言辅助；脚本执行、会话、管道与 UI 回调较多地位于 `TerminalPanel.kt`。
- `UuCommands.Ctx` 已有 cwd、cache、进度与取消回调，是业务门面的可用起点，但仍含本地化载荷。
- `TerminalPanel.runShell` 可以运行系统 shell；未来 MCP 不应未经区分地继承整个交互终端执行权限。

## 建议的共同架构

```text
Views UI / 交互终端 / 本地 MCP
                 ↓
         应用服务与任务执行层
      结果、调度、取消、进度、日志
                 ↓
      文件操作 / 格式能力 / JNI
                 ↓
            Rust 格式库
```

不是把所有操作统一为字符串命令。GUI、CLI、MCP 共同调用类型化服务；CLI 负责参数解析，GUI 负责交互，MCP 负责协议适配。

建议先按包建立边界，待业务依赖清楚后再决定 Gradle 模块拆分。避免把目录移动和协议改造同时铺满全仓。

## 错误与日志设计草案

### 一次任务只有一个可追溯身份

- OperationContext：operationId、来源、任务类型、格式、关联 tab/工作区、日志位置。
- OperationResult：Success / PartialFailure / Failure / Cancelled；已产出文件、失败成员和清理状态必须可查询。
- AppFailure：稳定错误码、阶段、相关路径/条目、技术原因、可重试性、关联日志。底层不生成本地化句子。
- CleanupIssue：作为主结果的附加问题保留；若删除失败造成半成品残留，必须在界面明确提示残留位置。

这些是待实现的契约名。迁移时复用现有结果类型并升级调用方，不长期维持两套协议。

### 用户必须看得到

- 失败和部分失败显示统一摘要，提供“查看详情 / 查看日志”，并保留任务历史；不只依赖短暂 Toast。
- 批量操作逐成员记录，最终给成功/失败统计；后续步骤依赖失败产物时必须停止。
- 页面已销毁或 tab 已关闭时，任务结果继续入历史，不向失效窗口弹框。
- 取消单独呈现；取消后的清理若失败，仍需呈现清理问题。取消不得被通用 catch 改写成成功或普通异常。
- 内部候选格式探测不匹配可记录诊断，不逐次弹错；全部探测失败时必须返回明确失败。

### .log 文件

- 任务开始即建立任务记录；日志按任务延迟创建或从开始创建，两者均需保证首次失败后立即可读。
- 建议默认写入应用 filesDir/logs/<operationId>.log，通过应用“日志”入口和失败详情随时预览，可导出到用户目录。
- 若采用输出目录旁自动写 .log，需要处理只读目录、失败时没有输出路径以及 FileObserver 刷新；内部日志仍是可靠的默认落点。
- 记录阶段、错误码、堆栈、输入/输出摘要、取消和清理结果；密码、密钥及原始敏感命令参数不得原样记录。
- 进度采样/节流；日志写入独立队列、限额轮转，预览按页读取，防止任务频繁写日志或大文件预览拖垮 UI。
- 日志写入自身失败时保留主错误，退到有界内存记录/Logcat，并明确显示“日志保存失败”；不递归记录自身错误。
- Kotlin/JNI 失败尽可能保留错误链；进程被原生崩溃或系统终止时无法保证最终错误落盘，下次启动需识别未完成任务并标为中断。

## UI 组件方案

借鉴 `tyranor-next` 的规则：同一语义只有一个实现入口，页面只提供数据、状态和动作；尺寸、颜色、反馈、禁用态由组件持有。

| 语义 | 建议入口 | 覆盖位置 |
|---|---|---|
| 主/次/危险/文字动作 | UuButton + ActionStyle | 解包、封包、删除、确认、取消 |
| 图标动作 | UuIconButton | 工具栏、列表附加动作 |
| 功能导航/执行条目 | UuActionRow | 设置、侧栏、操作抽屉；导航箭头与执行动作区分 |
| 布尔配置 | UuSwitchRow | 全局设置与格式选项 |
| 单选、多选、分段选择 | UuChoiceRow / UuSegmentedControl | 格式、模式、压缩等级 |
| 搜索与普通输入 | UuTextField | 搜索、命名、路径、密码；按身份配置 IME 和保密语义 |
| 顶栏/底部动作栏 | UuToolbar / UuActionBar | 文件浏览、预览、搜索 |
| 窗口与抽屉 | UuDialog / UuBottomSheet / UuSidePanel | 确认、选项、选择器、书签 |
| 卡片与分组 | UuSection / UuCard | 设置、首页、工具面板 |
| 空态、失败、任务反馈 | UuStateView / UuNotice / UuTaskCard | 全局统一反馈 |

先形成可预览的组件目录页，覆盖各状态，再迁移页面。建议规格草案：间距沿用 4/8/12/16/24dp；正文与标题按语义收敛；图标触控区至少 48dp，密集文件列表使用明确的紧凑规格。字体缩放时内容容器可增长，不能以固定高度裁字。

不直接复制隔壁 34dp 图标触控区、Compose/Miuix 实现或复杂动画。借用入口、职责和一致性机制；具体视觉规格在组件目录中统一验收。

窗口壳统一负责 ownerTab、返回/遮罩、键盘 Insets、横竖屏尺寸、叠层、关闭清理和手势。业务页不能自己再覆盖 onDismiss。保持壁纸 yielding、全部 tab 存活、Honor 禁用原生滚动条等既有不变量。

## MCP 可行性与最小范围

结论：方向可行，但当前需要先抽出无 UI 的任务和脚本运行器；不是只增加一个 HTTP listener。

- 建议显式开启本机自动化模式，监听 loopback 的 Streamable HTTP /mcp；协议版本按实际目标 Agent 支持情况协商并固定验收，不混用不同版本的传输细节。
- 同机目标客户端必须支持访问该端口；开端口不会让 Agent 自动发现或配置连接。容器/虚拟机客户端还需单独验证回环可达性。
- 工具草案：capabilities、command_help、run_uu(argv)、validate_uut、run_uut、task_status、task_cancel、task_log。脚本可定义解包→处理→回包步骤，任何依赖步骤失败即停。
- 长任务提交后返回 taskId，状态/日志/产物通过任务服务查询；HTTP 断连不被默认解释为任务取消。协议会话与业务 taskId 分离。
- 同一请求重试需要请求身份和产物策略，避免超时后重复封包；未完成任务可标记中断，不直接承诺进程重启后自动续跑。
- Agent 从 capabilities 与 help 获得格式能力、参数和限制；学习与执行基于现有同一命令注册表，避免另写一套帮助。
- 汉化内容可由 Agent 生成或应用用户已有补丁；MCP 提供文件和归档工作流，不保证任意游戏脚本都能自动翻译或回包兼容。
- 文件选择不能依赖弹窗：缺参返回类型化参数错误，密码/密钥通过明确参数传入，写日志前脱敏。
- loopback 不能区分同机其他进程，需本机令牌配对、Host/Origin 验证和工作区边界；默认不监听 0.0.0.0。
- 将普通 uu 命令、文件写入/永久删除、系统 shell 的能力分开。首版开放明确的 uu/uut 子集，脚本执行器采用执行策略；防止通过脚本或命令替换绕过工作区边界。
- 当前 Manifest、服务生命周期均需新增适配。先验证前台模式，再对长任务选择符合 Android 版本约束的后台执行方案，不能承诺开端口后永久存活。

规范依据：[MCP Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)、[Android 后台任务](https://developer.android.com/develop/background-work/background-tasks)、[Android 前台服务](https://developer.android.com/develop/background-work/services/fgs)。具体 SDK、服务类型及客户端兼容性尚未选型或验证。

## 建议实施顺序与验收

1. **可靠性基线**：修复合并错误检查/覆盖语义、共享原生状态的资源锁，以及测试临时目录竞争；先给关键问题建立能失败的回归。
2. **任务与错误闭环**：先贯通解包→合并→封包，再覆盖文件操作、转换、搜索、编辑和终端。验证部分失败、写盘失败、清理失败、取消、无前台窗口。
3. **UI 基础与样板**：组件目录 + 统一窗口壳；先迁移设置、侧栏和操作抽屉，再迁移浏览/预览/批量操作及编辑器外围。组件覆盖反馈、禁用/忙碌态、大字体、四语言、壁纸、手机/平板横竖屏。
4. **业务/脚本脱离 UI**：提取 TaskService、命令服务、UutRunner；同一任务从 GUI 和 CLI 执行，结果、错误、取消和产物必须一致。调度支持按原生库资源获取多个键，避免死锁并保持三槽约束。
5. **MCP 验证**：目标安卓 Agent 真实连接、调用 help、执行短 uu，再执行完整 uut 流程；验证任务查询、断连重连、取消、鉴权、路径越界及长任务后台行为。

每阶段独立可运行、可回归，不采用一次性全仓替换。Rust 改动跑 workspace 与对应真实样本；Kotlin/资源改动跑单测、Lint、四语言比较；JNI 改动跑完整 build.sh。UI 最终以真机验收为准，提交和推送仍遵循仓库审核规则。
